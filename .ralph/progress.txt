## 2026-10-30T20:55:00Z - KAN-080 - discussion run control
- Board revision `0005_discussion_run_control`: `discussion_runs` (status, autonomy, rounds
  requested/completed, token budget, time budget, stop reason, starter, timestamps),
  `discussion_rounds` (one row per executed round with answers/failures/repeats/tokens/elapsed) and
  plain columns on the existing tables (`round_count`, `run_state`, `tokens_used`, `elapsed_ms` on
  the thread; `round_number` + `content_sha256` on messages; `round_number` on votes). Everything is
  `op.add_column`, so the `cards` FTS5 triggers are untouched.
- `Orchestrator` is now the round engine: it executes one pass over the participants, records
  message + vote only when the position changes, hashes every answer, and reports answers, repeats,
  failures, tokens, elapsed time and whether the round was interrupted or hit a budget.
- `RunService` owns the loop and the control plane: `POST .../start` (inline single round),
  `POST .../runs` (202, always background), `GET .../runs[/{run_id}]`,
  `POST .../runs/{run_id}/pause|resume|stop`. The run row is the control channel - pause/stop are
  plain updates that the loop checks between participant calls and between rounds - and work runs on
  an in-process `ThreadPoolExecutor`, so no new infrastructure is involved.
- Termination rules: consensus, requested rounds used up, every participant failed, only repeated
  answers (`no_progress`), token budget after an answer, time budget after a round. One active run
  per thread; review is refused with `409` while a run is running or paused.
- UI: `RunPanel` in the discussion detail shows run state, round counters (`Rounds n · this run a/b`),
  tokens, elapsed time, pause/resume/stop and the per-round table, plus a "Run discussion" dialog for
  rounds and budgets. The panel polls every 1.5 s while a run is running. The board selector now asks
  for 200 boards instead of the default page.

## 2026-10-31T01:40:00Z - security - accounts, sessions and key hygiene (KAN-095)
- Roles stay simple on purpose: `admin` holds every scope, `member` every scope except `users:admin`.
  `has_scope` is now explicit, so a session's authority comes only from its role.
- Sessions are registry rows (`0005_accounts_and_sessions`). Logout, password change, role change and
  disabling an account revoke them; expiry is enforced on both the cookie and the row, and expired
  rows are purged at startup. Added `POST /auth/password`, `/users` CRUD with reset password, and
  last-admin protection (`409`).
- Sign-in is throttled per username and client address with exponential backoff; `X-Forwarded-For`
  is only trusted with `TRALALA_TRUST_PROXY_HEADERS=true`.
- API tokens default to 90 days, can be rotated in one step, and never receive `credentials:admin`
  or `users:admin`; discussion and agent scopes are now allowed on tokens. The board activity feed
  also requires `cards:read`.
- Weak or short `TRALALA_SECRET_KEY` values are replaced by a per-install secret; the first admin
  password is written to `<data>/.bootstrap-password` instead of the log; unhandled exceptions log
  the type only. `TRALALA_PREVIOUS_SECRET_KEY` re-seals stored provider keys at startup.
- Frontend: Settings gains the password form, the admin-only Users card and token rotation.
- Docs: decisions/0007, api.md, database.md, architecture.md, README, .env.example.

## 2026-11-02 - Worker surface: /llms.txt, /mcp and one tool catalogue

An external worker (an agent outside the installation, holding a token) is now a first-class client:
it can read a Board and a Loop, understand the task from the documents, claim a Ticket, move it
between columns and ask the local agents. The local role agents stay readers: they are invoked by a
run, never authenticate, and never touch a Ticket.

- `services/agent_tools.py` is the single catalogue: name, description, JSON Schema, required scope
  and a handler that calls the same services as REST. Seven tools: `read_board`, `read_loop`,
  `read_ticket`, `assign_ticket`, `move_ticket`, `comment_ticket`, `ask_agents`. Board/list
  creation, Ticket creation, archiving, document writing and every human gate are absent by design.
- `POST /mcp` speaks MCP over JSON-RPC 2.0 (Streamable HTTP): `initialize`, `tools/list`,
  `tools/call`, `ping`; notifications answer `202`; `GET /mcp` answers `405`. Every method is
  authenticated, and `tools/list` is filtered to the scopes the token holds, so a worker never sees
  a capability it may not use. A refused tool is `-32602`; a failed tool returns `isError: true`
  carrying the API error code, so `version_conflict` and `human_action_required` surface as data.
- `GET /llms.txt` is the public bootstrap: envelope, Loop lifecycle, the rules that never change,
  the tool list and the REST equivalents. No ids, no data, no secrets. nginx and the Vite dev proxy
  now route `/llms.txt` and `/mcp` to the backend, so an agent that tries `/llms.txt` gets text
  instead of the SPA shell with a 200.
- `GET /boards/{board_id}/actors` (`boards:read`) returns `people` (enabled humans, the only lookup
  a token cannot otherwise perform) and `agents` (enabled board profiles, honouring the board's
  selection). Without it `assign_ticket` could not name anybody: a token is its own agent actor and
  holds neither `users:admin` nor `agents:read`.
- `CardService.locate` resolves the owning Loop from a Ticket id, so board-level callers stop
  guessing; `move_ticket` accepts a column name and reads the version itself, retrying once when a
  concurrent write wins.
- `read_ticket` returns `allowed_actions` derived from the Ticket (archived, human-only, planned but
  not ready) plus the Loop's `execution_allowed` for context - a manual Ticket in a draft Loop is
  still movable, which the API always allowed.

  disables the agent actors behind them; re-enabling does not resurrect a revoked key.
  `GET /users` gains `agent_access_count` and `agent_access_last_used_at`.
- `GET /meta` publishes `member_token_scopes`, `member_token_limits` and `can_issue_tokens`.
- UI: a single `InteractionAccessCard` for everyone ("Interaction agent access": name, scopes,
  last used, expiry, rotate/revoke, plus a copy-ready MCP block), and an admin-only "All agent
  access" list; the Users card shows the per-person count and spells out what Disable does.
- Tests: `tests/test_interaction_access.py` (8 tests: member token drives MCP, forbidden scopes,
  expiry, cap, own-list isolation, rotate/revoke ownership, admin count + disable revokes,
  meta vocabulary), plus updated `test_accounts.py` and a new e2e journey.

Decision: `docs/decisions/0017-interaction-agent-access-ownership.md`.

## 2026-11-02 - In-card guide: "How do I connect my computer?"

The interaction-access card now carries the five steps a person follows at their own machine, in the
same collapsible style as the repository token guide:

1. create the key for this machine and tick only the scopes the agent needs;
2. copy the token (shown once, stored hashed);
3. paste the `mcp.json` template (`https://<Your URL>/mcp` and a Copy button - the guide carries no host of its own, so it reads the same on every installation);
4. ask the agent to read a board - `401` means the key is wrong/revoked/expired, `403` a missing
   scope;
5. watch "last used" to confirm it is that machine connecting, and revoke when done.

`frontend/src/features/settings/AgentAccessGuide.tsx` keeps the words general (no installation name or host,
no example token), and the snippet comes from `lib/agentAccess.ts`, so the card and the guide cannot
show different endpoints. The duplicate config block that used to sit below the list is gone; the
guide owns it. Verified in the running UI (expanded guide screenshots) and by extending the member
e2e journey to open the guide and assert its steps.
